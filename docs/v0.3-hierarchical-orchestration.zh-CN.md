# Goldilocks v0.3：分层动态编排

[English](v0.3-hierarchical-orchestration.md)

v0.3 将 Goldilocks 从一层式工作流路由器升级为动态组织协议。用户负责方向和结果；Lead 负责理解意图、总体规划、资源调度、共享接口和最终质量；Standard 负责一个具体板块，并可把完整执行合同继续交给 Fast；Fast 负责实现和聚焦验证，但属于叶子成员。

## 路由顺序

1. 先搜索同项目、同任务形态的已验证执行路径。
2. 做一次常数级“直做还是委派”判断。
3. 由 Lead 解决产品、架构、授权和共享接口决策。
4. 选择最浅的有效组织：Direct、Lead→Fast、Lead→Standard 或 Lead→Standard→Fast。
5. 在平台容量、隔离条件、集成风险和审核吞吐允许范围内，并行所有已经就绪的独立节点。
6. 证据逐级汇总，Lead 重跑组合验收。
7. 只有组合验证通过且任务可能复发时，才保存执行路径。

角色在拆解之后判断。Fast 表示剩余自主判断低，不表示改动小；Standard 表示板块内仍有局部判断，不表示任务中等；Lead 表示拥有决策权和最终责任，不表示必须亲自写完代码。

## 经济目标

质量、安全、授权和工具适配属于硬门槛。有效路径再比较：

- 按当前账户系数与通道稀缺度计算的额度加权消耗；
- 真实关键路径；
- 相比 Direct 或已验证相似路径的总 token 增长；
- 重试、审核和集成债务。

只要质量不下降，略多的低系数或独立额度工作模型 token 可以换取更少的稀缺 Lead 额度和更短时间。额度信息缺失时保持未知，Goldilocks 不编造系数。

## 上下文与升级

Fast 通常不继承父对话，只接收一个自包含执行合同；Standard 接收板块合同和最多四轮必要上下文；当关键决策确实散落在对话中时，明确的 Lead 交接可以继承完整历史和父 Lead 模型。

工作成员允许一次边界明确的修复；第二次失败或需求偏离后停止循环并重新分级。Standard 不得修改共享接口、扩大范围或跨越授权。多个 Standard 可以独立研究困难问题，但必须由一个负责人决策和集成。

## Codex 双通道工作成员

Codex 路由必须以所选调用通道真正支持的模型为准：

1. 宿主原生公开所选模型时使用原生子智能体。每次调用都声明 `fast__`、`standard__` 或 `lead__`，显式设置 `fork_turns`；除合理的完整历史 Lead 继承外，还必须显式选择模型。
2. 所选合格 Fast 模型不在原生模型列表中、但 `codex exec` 可以使用时，调用 Goldilocks Skill 打包的 `dispatch_codex_worker.py`。当前适配器把 `coding` 映射到 GPT-5.3-Codex-Spark，把 `general` 通用非编程生产映射到 GPT-5.6 Luna。
3. 两条通道都无法通过能力与质量门时，明确改选其他 Fast 模型、升级到 Standard 或留在本地执行，绝不静默继承 Lead。

外部适配器从文件读取一个完整合同，通过标准输入传给 Codex，按声明的工作类型固定模型，并且只关闭继续创建 Agent 的能力。默认 `project` 档位使用干净的 worker home，隔离无关的全局插件、App、MCP、Skill 与 Hook，同时保留项目规则、认证、供应商选择、模型元数据和打包运行库；`minimal` 还会忽略 execpolicy 规则；只有合同明确需要时，`inherit` 才保留完整用户环境。适配器把沙箱限制在只读或工作区可写，并原样返回 worker 退出码。并行写入仍必须使用隔离 worktree。Lead 或 Standard 必须检查真实 diff 与证据；进程正常退出本身不算验收通过。

Fast 是组织角色，不是某个模型的别名：Spark 是编程默认，Luna 是通用非编程生产默认。可替换单元也不等于单独启动一次 worker；没有既有经济性证据时，先用一个会话承接一个连贯批次，只有实测并行收益足以覆盖上下文和审核成本时才增加会话。

这一区分来自真实证据：2026-07-25，已安装的 Codex `0.146.0-alpha.3.1` 原生 collaboration 工具只公开 Sol 与 Terra，但同一安装包的 CLI 可以成功启动准确的 Spark 模型；更早的 `0.144.0-alpha.4` 日志中还有 22 个真实 `codex_exec` Spark 工作会话。它证明这段宿主版本需要双通道，不代表未来模型目录永远如此。

## 执行经验与审计

项目执行经验只保存已经验证的路径、前提、失效条件、角色结构、模型类别、证据、返工、耗时以及已知的额度和总 token 观察。它不保存 prompt、凭据、隐私数据或原始日志，也不进入面向用户的 changelog。

Codex Hook 将原生通道的匿名路由观察写入 `PLUGIN_DATA/orchestration.db`。SQLite 避免并发写入损坏；只有关联唯一时才核验实际模型，存在歧义时只记录不可验证，不会错误指控或停止某个子智能体。部分专用原生路径可能绕过 `PreToolUse`，因此未规划的 Sol 子智能体会在 `SubagentStart` 收到一次柔性的“继续还是退回”检查。观察到停止不等于 Lead 验证通过。

## 发布验收

当前编排层的结构验收覆盖嵌套路由、上下文边界、Fast 叶子约束、并发安全审计、版本元数据、唯一可见 Skill 和全部内部引擎路由。性能是否成功仍需真实项目证明：最终质量不劣于原方案、Lead 额度占比下降、总 token 变化受控、可并行项目关键路径缩短，并且集成缺陷不增加。
