# Agent 工作流评测经验

[English](benchmarking-lessons.md)

这些做法来自 v0.5.0 冻结发布矩阵及其离线审计。它们是方法说明，并不宣称所有工作流或宿主都会得到相同行为。

## 先分类失败，再使用结果

在账本中严格区分三类：

- **参与者失败：** Agent 已完成的工作未通过指定验收。
- **Harness 失败：** driver、完成状态谓词、范围规则或 grader 错误分类了结果。
- **基础设施失败：** provider、事件流、文件系统或传输阻止单元到达产品结果。

只有参与者失败能够支持产品质量结论。每一行及其原始遥测都应保留，但不能把 harness 或基础设施失败改写成产品缺陷或质量排名。

## 走真实的激活路径

直接调用 Hook 脚本，不能证明宿主真的会激活它。应使用已安装的 fixture、新建宿主任务，并将发现/激活证据与参与者工作分开记录。预期子 Agent 名称缺少前缀，是 Hook 或 Skill 未加载的有用信号；它不是路由质量的证据。

## 用量应由宿主计量

Usage 应来自宿主遥测，而不是参与者文本或参与者侧计费命令。宿主尚未给出检查点时，Usage 应视为不可用；保持静默，不能估算或报 0。这样可以避免评测开销和自报用量改变被测对象。

## 按语义评分，不按偏好词汇评分

验收测试应检查所需状态或行为，而不是某一个标题词等 token。在冻结 grader 前，加入肯定的同义表述 fixture 和否定的缺失状态 fixture。若审计发现词汇造成的假阴性，保留原始行、离线修正并公开说明；不要为获得不同标签而重跑已经完成的模型单元。

## 把交互式工作流当成交互来驱动

助理工作流可能合理地询问审批、带推荐项的 A/B 选择、终止性 yes/no，或确认是否可以先让 TDD 基线失败。driver 需要对这些预期门槛提供冻结的、保持需求不变的回复，并设置重复无进展提问的安全停止。不要把可回答但未识别的问题误当成参与者失败。

## 将官方成本和授权代理池分开

公开时应明确标出有公开费率模型的官方小计。模型来自没有公开数值费率的额度池时，另行命名比较估算。本版本的归一化成本是官方小计加用户授权的 Luna-equivalent Spark 代理；它不是账单，也不能这样描述。

## 冻结协议并维护账本

模型调用前，冻结输入、隐藏验收、对照臂身份、顺序、模型/宿主配置和核算规则。账本记录提示词封套、结果状态、耗时、Raw Token、模型组合、成本边界以及每个例外。不要自动重跑计分单元：保留该尝试，分类原因，并只在明确规则下显式授权重试。

## 将连续性和所有权分开

fresh session 可以从持久证据继续，不必重放旧工作。但这不等于可以把已知的可变执行链拆给多个负责人：一名负责人应完成已知的完整链，Lead 只做一次最终组合验收。应独立评估会话连续性和所有权边界。
