# Goldilocks 0.6.0 重构规格

```yaml
version: 0.6.0
status: confirmed
date: 2026-09-04
release_gate: implementation + clean_install + focused_acceptance + three_arm_comparison
```

## 1. 目标终态

`0.6.0` 是一次轻量重构，而不是在 Beta10 上继续堆功能。它应当：

1. 完全移除 Goldilocks Hook 运行面，不在每轮提示、启动、压缩或停止时启动后台流程。
2. 固定执行顺序为“消息归类 → 需求对齐 → 确定项目记录 → 路由编排 → 执行与连续性 → 验收、更新与交接”。
3. 让项目文档成为可核验的工作证据，但只在真实事件触发时读写，不把文档维护变成常驻流程。
4. 保留 Direct-first、四个原生 Agent、按需 Usage、按需诊断、路由回执、Night Shift、安全与权限边界。
5. 通过一次 Goldilocks 自有范围内的清洁安装，确保本机只有一个生效版本，身份统一为 `0.6.0`。
6. 以同题三臂测试比较 Beta9、v0.6.0 发布候选和不加载任何 Goldilocks Skill/规则的原生 Direct；通过发布门后才发布。

核心原则：**刚刚好的流程——质量、权限、安全和验收不降级，只增加能改变结果的步骤。**

## 2. 范围与非目标

### 本次包含

- 无 Hook 的原生 Plugin/Skill 工作流。
- 六步主流程及“先对齐、后编排”的顺序约束。
- 对插入消息的分类和主线返回点保护。
- 工作单元级 Spec/Plan，以及事件触发的 PROJECT、ACTIVE、handoff、debug、ideas、CHANGELOG 记录。
- ACTIVE 作为唯一执行前沿；不向宿主全局配置注入 Goldilocks `compact_prompt`。
- Direct-first 和最小充分验证，禁止无证据的重复等价测试。
- 四个原生 Agent 及现有模型路由、回退和 Sol 审查边界。
- 显式 Usage、显式诊断、路由结果记录和用户可见回执。
- Bootstrap 的预览式清洁安装、唯一版本检查和安装后验证。
- Beta9/v0.6.0 发布候选/纯 Direct 的简单三臂对照。

### 本次排除

- 替换 Codex 自身的压缩算法或维护完整聊天历史。
- 后台 Usage、后台更新检查、后台路由审计和任何形式的 Hook 恢复。
- 每轮读取 ACTIVE、全部项目文档或历史计划。
- 覆盖 Codex 自带压缩提示，或维护 Goldilocks 自有的全局 `compact_prompt`。
- 为每条消息、每个命令或每个微步骤创建 Spec、Plan 或工作包。
- 未通过发布门时自动发布。

## 3. 六步主流程合同

| 阶段 | 按需调用的能力/Skill | 必须完成的功能 | 按需读取 | 事件触发写入 | 退出条件 |
|---|---|---|---|---|---|
| 1. 消息归类与主线恢复 | Goldilocks 根规则；continuity | 将消息判定为 `NEW / QUESTION / ADD / REPLACE / PAUSE / CANCEL / CONFIRM / RESUME`；保存原主线和回答插话后的返回点 | 当前消息与近期上下文；仅恢复旧任务时检查 ACTIVE 元数据 | `ADD` 影响当前范围时更新对应记录；范围外想法写 ideas；暂停/恢复边界更新 ACTIVE | 已明确当前主线、消息影响和是否需要恢复 |
| 2. 需求对齐 | align（含按需头脑风暴）；任务对应的领域 Skill | 先查事实，再识别会改变终态的模糊点；必要时提出准确问题、推荐选项和主要取舍；得到明确终态、约束、非目标与验收 | PROJECT、既有 spec、相关代码/资料 | 非简单工作写入或更新 spec；稳定结构/边界变化更新 PROJECT | 决策前沿为空，或剩余分支已明确为非目标 |
| 3. 确定项目记录 | continuity | 选择本次最小充分记录：无流程文档、单工作包，或独立 spec/plan/ACTIVE/handoff | 项目现有文档惯例和当前工作包索引 | 只创建已被任务规模或状态事件触发的记录 | 已确定记录形态，且没有空模板或重复层级 |
| 4. 计划与路由编排 | build；kernel/orchestrate；model-routing | 先按 Spec 形成可执行 Plan，再比较 Direct/Fast/Standard/Mixed；明确依赖、单 owner、接口、整合顺序和验收 | spec、PROJECT、已有 plan、已验证路由事实 | 非简单多步工作写 plan；跨会话/等待/委派边界创建或更新 ACTIVE；实际交接才写 handoff | 每个执行单元都有 owner、依赖和验收；路线基于净收益而非展示需求 |
| 5. 执行与连续性 | build/TDD；diagnose；continuity；evolve；领域 Skill | 连续执行已对齐工作；处理中途消息后回到主线；查复用型 debug；捕获范围外 idea；做最小充分验证 | 当前 plan、匹配的 ACTIVE、相关 debug、领域资料 | 在连贯里程碑更新 plan/ACTIVE；满足复用条件才写 debug；明确延期才写 ideas | 实现达到 Spec，或出现必须重新对齐的阻塞 |
| 6. 验收、更新与交接 | prove；continuity；final-output-hygiene | 对照 Spec 映射声明与当前证据；检查最终差异；更新项目事实；完成真实交接并关闭活动状态 | spec、plan、当前验证证据、最终 diff/status | 更新 plan/spec/PROJECT；已验证用户可见变化写 CHANGELOG；真实 owner/阶段切换写 handoff；关闭或移除 ACTIVE | 每项完成声明均有当前证据，持久记录不再把已完成工作标成 active |

### 3.1 对齐先于路由

Direct 只代表少编排，不代表跳过需求判断。清晰、低风险且没有分歧的请求可以在常量时间内完成对齐并直接执行；存在会改变产品结果、架构、成本、权限、安全或验收的模糊点时，必须先对齐，不能先派任务再补问。

### 3.2 插入消息处理

- `QUESTION`：回答问题后自动回到原主线，不改变目标。
- `ADD-accepted`：明显相关、与已确认目标兼容且不增加权限/风险，直接更新 Spec/Plan/ACTIVE 中真正受影响的部分后继续。
- `ADD-pending`：有价值但当前存在疑问且不阻塞，记录为待议，继续不受影响部分，并在自然节点或任务结束时给出建议。
- `ADD-blocking`：会导致返工，或改变终态、架构、成本、权限、安全、验收，暂停受影响部分并返回需求对齐。
- `REPLACE / PAUSE / CANCEL`：只有用户明确表达时才改变或终止主线。

## 4. 项目记录合同

### 4.1 记录形态

> Spec 和 Plan 的语义必须存在于非简单工作；物理文件可以合并。

| 工作形态 | 记录方式 |
|---|---|
| 清晰、一次可完成的简单 Direct | 默认不创建流程文档 |
| 中等、单 owner、一次会话内可完成 | 一个 `docs/work/<topic>.md`，仅保留需要的 Spec、Plan、Status、Handoff 小节 |
| 多阶段、跨会话或需要独立验收 | `docs/work/<topic>/spec.md` + `plan.md`；只有发生持久化边界时再加 ACTIVE/handoff |
| 多 owner、长期项目或架构重构 | PROJECT + 独立 spec/plan；ACTIVE、handoff、debug、ideas、CHANGELOG 仍按事件触发 |

同一个工作单元跨多个对话时继续使用原 Plan；不会因换对话而新建 Plan。新的可验收目标才建立新的工作单元。项目级里程碑可以存在于版本 Plan，但不得成为永久追加的总账本。

### 4.2 读写触发器

| 记录 | 何时读取 | 何时写入/更新 | 完成后的处理 |
|---|---|---|---|
| `docs/PROJECT.md` | 新项目、结构性改动或需要理解稳定边界时 | 项目建立，或已确认的稳定结构、职责、入口、依赖方向发生变化时 | 长期保留当前事实，不堆叠编辑历史 |
| 工作单元 `spec` | 对齐、规划和验收当前工作单元时 | 非简单工作对齐完成；目标、范围、约束或验收被用户确认改变时 | 标记完成并保留为需求证据 |
| 工作单元 `plan` | 执行和交接当前工作单元时 | 非简单多步工作开始前；实现顺序、owner、依赖或验证方式发生有效变化时 | 标记完成并归档；不再作为活动指令 |
| `.goldilocks/ACTIVE.md` | 仅在 startup/resume/compaction/等待/委派/跨会话恢复，且状态、任务、session 匹配时 | 工作确实跨上下文边界、中途 steering、长等待、委派或交接时，在连贯里程碑更新 | 结果转入持久记录后关闭或移除；新任务不读取旧 ACTIVE |
| `handoff.md` | 接收 owner、对话或阶段交接时 | 实际发生交接，且接收方需要目标、当前状态、证据和下一步时 | 接收方核对后保留为交接证据，不常驻注入 |
| `docs/debug/` | 出现相似症状，且旧记录可帮助定位时 | 根因非显而易见且可能复发，或涉及环境陷阱、安全/数据完整性、值得保留的失败路径时 | 长期按需查；不记录瞬时噪声和原始日志堆 |
| `docs/ideas.md` | 规划、回顾或明确处理延期方向时 | 有价值但不属于当前验收，并且需要跨会话保存时 | 保留 idea、价值、重访触发器和依赖；不预先设计实现 |
| `CHANGELOG.md` | 发布或查询用户可见版本变化时 | 变化已经通过当前验证且对用户可见时 | 长期保留；不写未验证修复和内部路由历史 |

通用约束：

- 未触发绝不创建；触发后写最少足够事实。
- 只在连贯里程碑更新，不在每条消息或每个命令后更新。
- 同一事实更新既有记录，不重复追加。
- 链接到详细证据，不复制聊天、完整日志或历史摘要。
- ACTIVE 保持短期前沿，目标上限约 4 KB/100 行；超出时将已完成事实转移到对应持久记录，只保留当前目标、owner、状态、阻塞、证据、下一步和不重复边界。
- 仓库事实与当前 diff 优先于陈旧记录。

## 5. 保留能力与约束

### 5.1 必须保留

- 四个原生 Agent 配置：Spark Fast、Luna Economy、Terra Standard、Sol Reviewer。
- 已有模型身份、权限、质量、配额和回退约束；宿主给出的完全权限不得被 Goldilocks 私自降级。
- Direct-first；任务执行中出现新证据时允许升级到其他路线。
- 用户语言的 Goldilocks 活动提示和最终路由回执，但只显示本任务真实发生的动作。
- Usage 只在用户显式询问时读取一次；无数据时不重试、不诊断。
- 诊断、运行时检查、路由结果记录和验收工具只按需调用。
- Night Shift 作为按需路由模式保留。
- minimum-sufficient verification：一次权威证据已经证明声明时停止；产品修复后只重跑失败项和受影响项。
- 认证、数据安全、不可逆操作、正式发布等高风险边界按实际风险验证，不因减重而取消。

### 5.2 禁止恢复

- Hook 生命周期入口及同步/异步后台变体。
- 普通任务中的自动更新检查、自动 Usage、自动审计或网络请求。
- 为了“更保险”新增无法指出具体事故的 hash、contract freeze、baseline 或 gate。
- 原因不明时重复同一测试碰运气；应转入 diagnose，并选择下一项有区分度的检查。

## 6. 清洁安装合同

Bootstrap 的清洁安装是一次显式安装/升级/修复流程，不进入普通任务热路径。

1. 先准备可安装且所有 manifest 身份一致的 `0.6.0`。
2. 只枚举 Goldilocks 自有的活动安装、缓存、旧版本入口、旧 Hook 信任/显示残留和重复 portable/native 入口。
3. 在任何删除前展示预览；应用只删除已识别的 Goldilocks 自有目标。
4. 必须保留 Git 仓库、版本历史、备份、用户项目文档（包括 `.goldilocks/ACTIVE.md`）、用户自定义文件、其他插件和无关宿主配置。
5. 只在顶层 `compact_prompt` 精确匹配已知 Goldilocks 当前或遗留内容时，将其列入清洁安装预览并删除；用户自定义 prompt 与 `experimental_compact_prompt_file` 一律保留并报告未处理。
6. 安装唯一的 `0.6.0`，不同时保留另一个生效的 Goldilocks 工作流入口。
7. 验证：版本身份一致、零 Goldilocks Hook、零 Goldilocks 全局 prompt、四个 Agent 可见且身份正确、显式 Usage/诊断可用、用户既有权限未被降低。
8. 提醒重启 Codex 或开启新任务，使旧进程和旧会话快照退出；不把 UI 缓存残留误报成运行时 Hook。

清洁安装不得以“干净”为理由删除用户工作或修改无关全局设置。

## 7. 验收与发布门

### 7.1 静态与聚焦验收

- 所有公开 manifest、安装源、版本展示和发布材料统一为 `0.6.0`。
- Plugin 元数据不注册 Hook；源码、Bootstrap 和文档不再把 Hook 声明为运行依赖。
- 六步顺序、消息分类、记录触发器和 ACTIVE 恢复条件有可执行合同与聚焦回归检查。
- 四个原生 Agent 配置仍在，模型/思考等级/角色边界没有被静默改变。
- 显式 Usage、显式诊断、路由记录和最终回执仍可用。
- Bootstrap 清洁安装的预览、保留边界、唯一安装和检查路径通过聚焦测试。
- 清洁安装能移除已知 Goldilocks `compact_prompt`，且不覆盖、删除或误认用户自定义/实验压缩配置。
- ACTIVE 的静态合同、旧任务拒绝条件、清洁安装与零 Hook 边界必须通过。真实压缩续接最多做一次聚焦探针；若宿主在进入恢复事件前未完成首轮，则如实记为 unknown，不伪装成通过或失败，也不重复运行碰运气。用户可明确决定是否将该宿主证据缺口转为发布后的实机观察。
- 运行受影响的既有测试；已被明确删除的 Hook 行为测试不得作为失败重新引入。

### 7.2 简单三臂行为对照

使用一个固定、低风险、边界清晰、应走 Direct 的小型代码修复题；题目必须有一个现成或很小的确定性验收，不需要外部网络或额外领域插件。

三臂：

1. `0.5.3-beta.9`；
2. `0.6.0`；
3. 纯 Direct：不加载任何 Goldilocks Skill、Plugin、Hook、compact prompt 或 Goldilocks 全局规则。

控制条件：同一题目、同一干净 fixture、同一宿主、同一主模型与思考等级、同类新任务/冷上下文、相同权限和工具；每臂只跑一次有效样本。基础设施失败可以替换该臂一次，但不得通过重复运行挑选最好成绩。

记录：

- 质量与验收结果；
- wall time；
- Raw Token；
- observed normalized cost 与 cache-neutral cost；只有双方缓存命中/写入占比的精确差异不超过 5 个百分点时，前者才作为硬比较，否则保留前者用于报告，并以“全部输入按同一 uncached 费率、输出照常计价”的后者判定；
- 工具调用、子 Agent 启动、用户往返、额外流程文档、验证恢复次数和重复验证次数；同一代码代、同一语义验证先因 126/127 未启动，随后由可用 runner 成功完成，只计为一次可见恢复，不计作重复产品验证；
- 实际路线及是否出现不必要的 ACTIVE/Plan/测试。

发布判定：

- 三臂均完成同一质量验收；v0.6.0 候选不得通过降低功能、权限、安全或验收换取速度。
- v0.6.0 候选在简单题中必须保持 Direct 行为：不委派、不建立不必要状态、不运行后台能力、不重复等价验证。
- v0.6.0 候选相比 Beta9，在 wall time、Raw Token、按上述规则选择的 cost basis 三项中，单样本差异不超过 `+3%` 视为等效/不差；至少两项须达到该条件，且任一项不得超过 `+10%`。
- v0.6.0 候选相比纯 Direct 的 wall time 与按上述规则选择的 cost basis 各自差距不超过 `+15%`；Raw Token 单独报告，不另设隐藏硬门，若偏高必须有可归因且非重复流程的解释。
- 若单项结果明显受基础设施、缓存或服务端抖动污染，只替换受污染样本一次并保留原始记录；仍无法解释时不发布，不扩大成完整矩阵碰运气。

### 7.3 发布条件

只有 7.1 与 7.2 均通过，清洁安装后的本机状态也通过检查，才允许：

- 更新中英文 CHANGELOG/README 的已验证内容；
- 创建 `0.6.0` 发布提交和标签；
- 推送并发布 `v0.6.0` 正式版。

任何发布动作仍须遵循用户已明确授权的目标和仓库；测试通过不是向其他仓库、商店或生产环境扩张权限。
