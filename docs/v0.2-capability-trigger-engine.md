# Goldilocks v0.2 — Capability & Trigger Engine

## Goal

Replace Superpowers-level capability coverage with less mandatory process and less loaded context. Implement only gaps demonstrated by fresh-context RED evaluations.

## Capability engines

| Engine | Coverage |
|---|---|
| Align | Brainstorming, Grill frontier, design, requirements, authority boundaries |
| Diagnose | Systematic debugging, root cause, failed-hypothesis escalation |
| Build | Reuse/native-first, planning, TDD, implementation |
| Orchestrate | Worktrees, parallel work, capability routing, integration ownership |
| Prove | Review, verification, real runtime, branch finishing |
| Evolve | Idea ledger, skill writing, process improvement |

## Thin explicit entries

`brainstorming`, `debugging`, `tdd`, `planning`, `worktrees`, `parallel`, `review`, `verification`, `finishing`, and `writing-skills` remain discoverable entry points. Each should route into the relevant engine in no more than 80 body words.

## Hard budgets

- Main router: at most 650 words.
- Thin entry: at most 80 body words.
- Direct path: main router only.
- Ordinary feature path: at most 1,500 rule words at any stage.
- Single coherent workflow: zero agents by default.
- No material ambiguity: zero extra user rounds by default.
- All capability documentation: at most 6,000 words.
- Every added rule: backed by a reproducible failing evaluation.

## RED before capability expansion

The 50-case suite fixes expected routing and budgets before v0.2 implementation. Baseline responses must be produced in fresh contexts without the expected answer or another arm's output. Failures are captured verbatim and converted into the smallest engine or entry change that closes the observed gap.
